## 三、本周工作时间线

### 周一（9 月 21 日）

1. 修复安阳热轧演示环境无法访问的问题，完成 CRP 图扑 License 更新及端口冲突处理。

### 周二（9 月 22 日）

1. 根据当前高频点位数量需求重新划分采集消息，并通过日志观察实际采集频率。各个 50 ms 任务中均为 REAL 类型点位，板型任务中的点位均位于同一 DB 块，其他任务中的点位存储在多个 DB 块。
2. 与彭浩沟通确认采集器实现方式：每个任务创建独立连接，采用非阻塞并发读取，目前基本没有优化空间。
3. 梳理实验室采集情况：实验室使用 S7-1200，通过 aTrust VPN 中转的平均 Ping 延时为 30～40 ms；6 个 50 ms 任务基本可以控制在 50 ms 左右，每个任务约包含 20 个点位，且点位均在单个 DB 块内连续存储。
4. 分析轧机端采集条件：轧机端 PLC 为 S7-400，CPU 性能一般；所需点位分散在不同 DB 块且在块内非连续存储，一级重做 DB 并使点位连续存储可以提高读取效率。

### 周三（9 月 23 日）

1. 基于 Apache PLC4X 测试单连接读取全部点位、单连接分三个请求读取全部点位、按相近 DB 地址每 400 字节分批读取并在本地解析类型，以及多连接分批读取等方式。
2. Apache PLC4X 代码实现采用并发发送请求，但实际测试中请求未被并发处理，可能是底层对请求进行队列处理，也可能是 PLC 对单连接请求进行队列处理，因此改用 Snap7 实现。
3. 基于 Snap7 测试单连接读取全部点位、单连接分三个请求读取全部点位、按相近 DB 地址每 400 字节分批读取并在本地解析类型，以及多连接分批读取等方式。
4. 测试结论：单连接一次请求全部点位无法满足 50 ms 需求；单连接多批次并发请求可能被 PLC 侧队列处理，Apache PLC4X 和 Snap7 均出现类似情况；多连接、多批次请求配合本地类型二次解析可以满足 50 ms 需求。
