# 独立对外服务实例与 ZRM1 历史道次补全方案

## 1. 总体设计与已确定口径

同一份代码、同一个 JAR，通过运行模式区分两类实例：

- **机组跟踪实例**：继续负责指定机组的实时订阅、算法计算和结果发送。
- **对外服务实例**：不绑定机组，提供历史补全接口，按业务请求读取指定机组配置和历史数据。

第一期实现 ZRM1 道次补全，整体流程为：

```text
提交时间范围 → 返回任务号 → 获取 Cube 配置与点位元数据
→ 查询道次历史 → 识别递增切换事件 → 计算上一道次首末帧
→ 查询历史重复生产次数 → 调用质量接口 → 查询任务结果
```

按照本次确认，采用以下业务口径：

| 项目 | 确定规则 |
|---|---|
| 时间范围 | 上海时区，左闭右开 `[startTime,endTime)` |
| 补全对象 | 切换时间落在请求范围内的上一道次 |
| 切换事件 | 道次号由小变大；回退不结算 |
| 速度条件 | 严格大于 `rolling.quality_min_speed` |
| 首末时间 | 上一道次内第一帧、最后一帧速度达标数据的 `ts` |
| 入口卷号 | 沿用实时质量口径，从末帧的**开卷侧**获取 |
| 出口长度 | 从末帧的**卷取侧**获取 |
| 出口厚度 | 从末帧的出口厚度实际值获取 |
| 左边界回溯 | 固定向前 1h；无法确认完整起点则跳过 |
| 右边界 | 不向后查询；未出现递增切换的末尾道次不提交 |
| 跨点位对齐 | 使用帧时间之前或相同时间的最近值，默认最大滞后 5 秒 |
| 执行方式 | 异步任务，任务和结果仅保存在内存 |
| 重复提交 | 每次重新计算并写入，由质量接口负责覆盖 |

这里的“沿用实时质量口径”指设备选择、字段来源、速度阈值和请求转换；历史首末帧按速度确定，不重放实时算法的长度趋势窗口。

## 2. 运行模式与接口设计

### 运行模式隔离

新增 `tracking.mode`，支持 `unit`、`external`，默认 `unit`，保证现有部署兼容。

对外实例配置示例：

```yaml
tracking:
  mode: external

history-backfill:
  lookback: 1h
  point-max-age: 5s
  max-range: 24h
  page-size: 2000
  worker-count: 1
  queue-capacity: 10
  result-retention: 24h
```

`external` 模式不要求配置 `tracking.unit`；`unit` 模式启动时校验机组代码非空。

需要对实时入口及其依赖链实施条件装配：

- 不启动 `TrackingRunner` 和点位订阅初始化。
- 不装配 MQTT adapter、消息监听入口和实时任务生产入口。
- 不装配 RocketMQ 生产者、消费者及消费容器。
- 对外部署 profile 排除已核实的 `org.apache.rocketmq.client.autoconfigure.RocketMQAutoConfiguration`。
- 历史补全不调用实时配置刷新、运行态保存或重复生产次数分配方法。

对外实例业务依赖为 Cube API、TDengine 查询端点、PostgreSQL 和质量接口。已有 Redis 相关公共组件若保留装配，不得被补全路径调用或成为对外实例启动条件。

增加对外部署 profile，以 `prod,external` 等组合启用；环境地址和凭据通过外部配置注入。

### HTTP 接口

扩展现有空的 `ReTrackingController`，第一期提供：

**提交任务**

```http
POST /openapi/retracking/zrm1/status/pass-output
Content-Type: application/json
```

```json
{
  "startTime": "2026-10-09 00:00:00",
  "endTime": "2026-10-10 00:00:00"
}
```

- 严格解析 `yyyy-MM-dd HH:mm:ss`，固定使用 `Asia/Shanghai`。
- 要求 `startTime < endTime`，默认跨度不超过 24h，结束时间不得晚于受理时间。
- 请求体不传机组，业务目标固定为 `zrm1`，不代表实例归属于该机组。
- HTTP 202，沿用项目 `R<T>` 包装，返回 `taskId`、任务状态及查询地址。
- 格式和范围错误返回 400；队列满返回 429，不在 HTTP 线程执行补全。

**查询任务**

```http
GET /openapi/retracking/tasks/{taskId}
GET /openapi/retracking/tasks/{taskId}/passes?page=1&size=100
```

任务摘要返回时间范围、执行阶段、已扫描记录数、已识别事件数、成功/跳过/失败数量、创建时间、结束时间及错误摘要。

道次明细返回旧/新道次号、切换时间、生产首末时间、所选设备、质量请求数据、点位原始时间戳，以及处理状态和原因。

任务状态采用：

```text
QUEUED → RUNNING → COMPLETED / PARTIAL_FAILED / FAILED
```

没有事件或只有可解释的跳过项时为 `COMPLETED`；存在道次调用失败时为 `PARTIAL_FAILED`；无法继续完成扫描时为 `FAILED`，保留此前成功明细。

结果在结束后默认保留 24h；最多保留 1000 个已结束任务，达到上限时淘汰最早结束任务。不存在、过期或重启后丢失的任务返回 404。第一期不增加任务表、自动恢复或失败重试接口。

## 3. Cube 与历史数据读取

### 配置与点位定位

现有 Cube 转换分发器按 `tracking.unit` 选择机组，需要增加显式机组参数的查询能力，原方法继续委托当前实例机组，保持实时行为兼容。

新增历史配置入口，例如：

```java
StatusHistoryConfigSnapshot fetchStatusHistoryConfig(String unitCode);
```

每个任务执行时：

1. 调用现有 Cube API `/openapi/meta/tree`，沿用已有请求 DTO 和根路径配置。
2. 按机组和跟踪类型编码大小写不敏感定位 `zrm1/status`。
3. 复用 `StatusCubeApiTrackingConfigConverter` 转换算法配置。
4. 根据 `point_prefix` 和配置点位名称定位对应叶子节点。
5. 获取 `path`、`code`、`cubeKey`、类型、单位及有效标记。
6. 将算法配置和点位映射固化为本任务快照，执行过程中不受配置热更新影响。

需要解析的点位包括道次号、速度、方向、出口厚度及设备卷号和长度。

`direct_reverse` 沿用现有配置布尔值，空值按 `false`，第一期不新增反向点位配置。历史补全独立校验所需质量字段，不因实时 `enable` 或 `quality_output_enabled` 被关闭而禁止人工补全。

按技能中的规则推导 TDengine 对象：

```text
数据库：cube
字段：code
对象名：cubeKey 去掉末尾的 "_" + code
```

禁止把配置点位名称直接当数据库字段。后缀不匹配、必要节点无效、点位无法唯一定位或 schema 不匹配时，任务失败，不猜测映射。

### TDengine 查询适配器

新增领域接口 `PointHistoryRepository`，提供有序分页读取和指定时间之前最近值查询；基础设施实现通过 taosAdapter REST SQL 查询，复用现有 HTTP/Jackson 能力，不新增本地 TDengine 客户端依赖。REST 支持 SQL 请求及带时区的时间返回，错误需要同时检查 HTTP 状态和响应体业务码。[TDengine 官方 REST 文档](https://docs.taosdata.com/developer-guide/connectors-reference/rest-api/)

- 使用独立 `tdengine-history.*` 配置，不混用现有时序写入服务配置。
- 所有对象使用数据库限定名，如 `cube.<object>`。
- 仅开放读取和 schema 校验方法，不提供任意 SQL HTTP 接口。
- 标识符由已验证的 Cube 元数据生成，时间条件统一转换后生成。
- 时间内部使用 `Instant`，保存数据库原始精度；向质量接口发送时再按现有网关转换成上海时间秒级字符串。
- 同一对象的必要字段合并读取，跨对象由应用组帧。

现有 `TimeSeriesStorageFeignClient` 只有建表、写入接口，不能直接承担历史读取。

### 全量分页与帧对齐

道次号先独立读取 `[startTime-1h,endTime)` 的完整历史，按时间扫描，识别候选事件。随后按候选道次区间读取速度及必要字段，分页归集首末帧，避免加载整天原始数据。

- 默认每页 2000 条，以时间游标推进，跨页保留状态。
- 对象必须有确定排序；若 schema 显示同一时间可能存在多行，必须加入实际唯一排序键，不能仅按 `ts` 翻页。
- 不使用降采样、插值或聚合值代替真实切换事件。
- 单页返回数量或服务端上限不能当全量；持续读取到查询完成。
- 速度帧只使用真实速度采样时间，不填充速度。
- 道次归属由道次事件时间线确定，不对保持不变的道次号施加 5 秒失效限制。
- 方向、卷号、长度和厚度采用 `pointTs <= frameTs` 的最近一条记录；`frameTs-pointTs <= 5s` 才有效。
- 最近一条为 null 或非法值时视为缺失，不越过该记录寻找更旧的有效值。
- 默认 5 秒作为服务配置，不加入请求参数；字段明细保留来源时间，便于审计。

## 4. 道次计算、设备选择与质量写入

### 道次切换及边界

将道次时间线划分为连续段，每个段保留独立身份，不能只用道次号分组。例如两个生产周期中的“第 1 道次”是不同段。

- 有效生产道次号为整数 `1～999`；0 表示非生产状态，不能生成质量数据。
- 连续相同值不生成事件。
- `1→2`、`2→3`、`2→4` 均结算紧邻的旧段；跳号不生成未观测到的道次。
- 回退或归零结束旧段，但不提交该旧段；后续重新开始独立段。
- null 不产生切换，保留最后已知状态；非整数或越界值记录异常，并将受影响段标为不完整，避免跨异常拼接。
- 仅处理切换时间属于 `[startTime,endTime)` 的递增事件。
- `startTime` 正好发生切换时，结算前一道次；`endTime` 正好发生切换时，交由下一次请求处理。

对于 startTime 处已有道次，向前读取固定 1h。回溯窗口内必须观察到该连续段起点；若第一段从窗口左边界就已持续且起点不可确认，记录 `INCOMPLETE_LOOKBACK` 并跳过。必要的最近值种子读取不能被当作完整起点证明。

示例：请求从 00:00 开始，观察到道次 3 从前一天 23:40 持续至 00:12 的 `3→4`，则补全道次 3，生产开始时间允许早于请求开始时间。

### 首末速度帧

对上一道次区间 `[segmentStart,transitionTime)`：

```text
qualified = speed > quality_min_speed
startProdTime = 第一条 qualified 速度帧的 ts
endProdTime   = 最后一条 qualified 速度帧的 ts
```

- 不取速度绝对值，不把等于阈值视为达标。
- 中间停车不拆成多个道次。
- 不存在速度达标帧时记录 `NO_QUALIFIED_FRAME`。
- 只有一条达标帧时允许首末时间相等，并在明细标记单帧情况。
- 首末时间确定后不因末帧字段缺失而向前移动结束时间；末帧必要数据不足则跳过。

### 设备选择与字段生成

从实时 status 算法抽取无状态的设备选择规则，让实时和补全共同调用，原实时行为保持不变：

```text
effectiveDirection = rollingDirection XOR directReverse
```

| 实际方向 | 第一道次开卷侧 | 后续道次开卷侧 | 卷取侧 |
|---|---|---|---|
| false：右→左 | 右侧 POR | 右侧 TR | 左侧 TR |
| true：左→右 | 左侧 POR | 左侧 TR | 右侧 TR |

设备编码和物理位置来自 Cube 配置，不硬编码 `tr1/tr2`。第一道次方向缺少对应 POR，或设备对无法唯一确定时跳过。

在末帧组装：

| 质量字段 | 来源 |
|---|---|
| `unitCode` | `ZRM1` |
| `inMatNo` | 开卷设备卷号 |
| `outMatLength` | 卷取设备长度，单位 m |
| `outMatThick` | 出口厚度实际值，单位 mm |
| `cellCode` | 复用 `CellCodeResolver`，如道次 3 为 `ZRM1003` |
| `startProdTime/endProdTime` | 速度达标首末帧时间 |
| `inMatRepeatProdNo` | 按道次开始时间查询历史次数 |

复用卷号清洗规则，排除空白、纯句点和 `request color` 占位值；长度及厚度须大于 0。

同一段内若可用历史数据表明轧制方向或开卷卷号发生变化，记录 `INCONSISTENT_PASS_DATA` 并跳过，避免将不同生产身份拼成一条记录。

### 历史重复生产次数

扩展 `RepeatProdNoRepository`，新增只读方法：

```java
Integer findMaxBefore(String unitCode, String coilNo, Instant passStartAt);
```

新增 Mapper 查询：

```sql
SELECT MAX(in_mat_repeat_prod_no)
FROM qm_dc_repeat_prod_no_log
WHERE unit_code = #{unitCode}
  AND in_mat_no = #{coilNo}
  AND create_time < #{passStartTime}
```

- 使用速度首帧时间，而非道次号变更时间。
- 机组大写，时间转为上海 `LocalDateTime` 对应当前 PG 时间列。
- 未查询到记录时返回 1。
- 沿用现有历史最大次数语义，包含逻辑删除记录，避免生产序号回退。
- 不调用 `allocateNext` 或 `findLatestOrAllocate`，不写入次数表。
- `create_time` 为 null 的记录不能证明其发生于开始时间之前，不参与查询。

### 异步执行与失败处理

新增专用补全线程池，默认单工作线程、队列容量 10，同一任务按切换时间顺序处理。

质量调用直接复用：

```java
QualityServiceGateway.write(RollingPassOutput output);
```

继续调用 `/api/quality/material/cell-blood/output`，沿用现有 DTO 的 camelCase 字段、重复次数字符串和质量响应 `code=200` 的成功判断。无需另建一套质量协议。

不使用现有 `AsyncRollingPassOutputSubmitter`，因为其失败只记录日志，无法向补全任务反馈结果。

- 每道次复用现有最多三次尝试和退避策略。
- 成功、跳过或最终失败立即写入内存任务明细。
- 单道次失败后继续处理其他道次。
- 全局配置失败或道次扫描无法继续时终止任务，保留已处理结果。
- 新提交相同时间范围创建新任务，重新写入质量接口。
- 超时存在“质量已写入但本地未确认”的可能；不宣称恰好一次，依赖质量覆盖语义处理重试。

## 5. 实施顺序、测试与上线验收

### 实施顺序

1. 增加运行模式及消息入口条件装配，验证无机组的 external 实例可启动。
2. 增加显式机组 Cube 查询、点位元数据映射和任务配置快照。
3. 实现 TDengine 只读分页、最近值读取及时间转换。
4. 抽取共享设备选择规则，实现历史道次识别和末帧组装。
5. 增加按开始时间查询重复生产次数的方法。
6. 实现内存任务管理、后台执行及三个 HTTP 接口。
7. 补充对外部署配置、接口说明和异常原因字典。

遵守现有 controller / application / domain / infrastructure 分层；历史处理不通过伪造实时消息触发 `StatusTrackingAlgorithmImpl.calculate()`。

### 回归测试

必须覆盖：

- external 模式无 `tracking.unit`、无 MQTT/RocketMQ 可启动；默认 unit 模式保持现有行为。
- 显式读取 ZRM1 配置不依赖实例机组；非法映射和配置缺失可诊断。
- 连续值、递增、跳号、回退、归零、null、非法值及跨页切换。
- 切换发生在 startTime、endTime；回溯完整与不足；末尾无切换。
- 速度恰好等于阈值、负速度、停车后继续、无达标帧及单帧。
- 方向 XOR 反向、首道次 POR 与后续 TR、设备缺失、身份变化。
- 最近值在 5 秒边界、超过 5 秒、来自未来、null 记录及跨页最近值。
- 重复次数严格早于开始时间、开始时刻相等、未来更大次数、无记录默认 1。
- 质量成功、业务失败、超时重试及单道次失败后继续。
- 队列满、并发查询、结果分页、过期清理和内存结果上限。
- 首末原始时间精度及上海时间转换，避免八小时偏移。

运行新增针对性测试后执行 `mvn clean test`、`mvn clean package`。

### 联调验收与明确限制

当前会话未核实线上 schema 和质量接口覆盖行为，上线前完成以下验收：

- 使用只读查询确认 Cube 映射、TDengine 对象类型、唯一排序键、采样频率和字段单位。
- 选取包含跨午夜、换向及多个生产周期的历史样本，人工核对首末帧和质量请求。
- 在测试环境对同一道次发送相同及修正后的请求，确认质量接口覆盖且不会新增重复记录。若不支持，需先明确质量端覆盖协议，生产重写不能依赖未经验证的假设。
- 确认历史时期与当前 Cube 配置一致；第一期不提供按历史版本还原配置。
- 对外实例部署为单副本，任务查询必须访问同一进程；重启丢失任务是本期已选定行为。
- 日志记录任务号、事件和错误原因，不输出连接凭据；不记录整段原始历史。

完成标准：给定时间范围后，可查询到每次递增事件对应的补全结果，成功项能核对质量入参，跳过和失败项有明确原因；对外实例不启动任何机组实时订阅，也不修改实时运行态。
